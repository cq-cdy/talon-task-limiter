# 大数据与 CPU 复合任务验证

新增 `talon_task_limiter_workload_test`，与原有 API、生命周期、故障注入和历史测试并存。CTest 标签为 `workload`；每个场景串行启动，场景内部仍有多个执行器和并发提交者，超时为 300 秒。

```sh
ctest --test-dir build-release -L workload --output-on-failure
build-release/talon_task_limiter_workload_test \
  --gtest_repeat=5 --gtest_shuffle --gtest_random_seed=73129
```

## 四类实际计算

| 场景 | 最大规模与关键验证 |
| --- | --- |
| 批量 CPU 作业 | 1,048,576 个任务，32 个提交者、8 worker；每任务处理 16 个 64-bit 字，执行四轮混合、排序和摘要。使用不同排序算法逐项核对，检查执行/析构各一次、背压保留所有权、活跃 payload 上界以及长期保留的 262,144 个 future |
| 矩阵分解与 fan-in | 最大 256×256 整数矩阵，分块和 K 维拆分形成数千个计算/归并任务；直接 i/j/k 串行乘积作为 oracle，覆盖不整除的边界块、计算完成后的业务错误、CPU 计算中途关闭和未接纳分支的终结 |
| 多池数据 DAG | 三个执行器，四个并发数据流，每流最多 1,048,576 条记录；分片变换/排序、k-way merge、继续派生下一阶段，最多六级依赖。成功路径与整批串行排序逐项比较；失败路径核对原始错误消息和后续阶段未执行 |
| 析构驱动 continuation | 八条链、每链 96 步、16,384-word 大缓冲区；捕获对象析构时转交下一任务，额度为 1 时必须拒绝直接重入并转交外部提交者。覆盖同池直接续接、背压、Close 竞争、所有权转移、部分完成结果和最终清理 |

记录条数、矩阵运算和任务数量分别计算，不把“一个任务中的循环次数”当作多个调度任务。数据 DAG 最大配置每阶段有 4,194,304 条记录（约 32 MiB 原始记录）；四阶段处理 16,777,216 条阶段记录，测试保留了任务间真实的数据依赖。

## oracle 与并发约束

- 批量作业的任务采用标准排序，参考路径采用插入排序及不同循环顺序；输出和每个任务 ID 都独立核对。
- 矩阵任务采用分块、分 K 维的部分积，参考路径直接计算完整乘积；错误块必须保持未写入哨兵，不能用部分结果冒充成功。
- DAG 的任务分片排序后 k-way merge，参考路径每阶段整批排序。每个 stage/branch 有独立执行账本，错误后不允许生成下一阶段。
- continuation 参考路径按轮遍历缓冲区，任务按元素遍历；关闭可能发生在任意工作线程，已完成链和中途终止链分别校验。
- fan-in 用 acq_rel 递减链发布分支结果，再通过执行器队列发布给归并任务；不假设回调“恰好在同一线程”。

所有重试都属于明确的外部提交者。worker 和析构回调遇到满载不等待自身额度；continuation 保留 move-only 请求，交由外部队列重提。矩阵关闭场景会将拒绝的分支也记入 fan-in，否则下游可能永远等不到结果。

CPU 关闭测试用计算中途的门闩控制时序；不使用 sleep 猜测“应该已经开始执行”。continuation 不假设到达关闭阈值后立刻获得 CPU，因此按真正 Close 之后的观察值校验排空上界。

这些是正确性和负载测试，不是吞吐性能基准。具体执行结果记录在 [verification.md](verification.md)。
